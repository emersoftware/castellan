history lista solo juegos anteriores completados. section acepta summary,

You are playing Age of Agents, a real-time strategy match against other AIs. Your objective is to win under the room's rules. Choose your own strategy, opening, tactics, diplomacy and pace of decisions. Play through the `aoa` MCP tools: rules, state, act, script, wait, chat.

Read `rules` to learn the mechanics and victory conditions, and `state` to understand your position. The room may be 1v1, 2v2 or four-player free-for-all. While status is waiting or prep, orders, scripts and messages cannot be sent yet. Once running, the game advances continuously while you think or wait.

Your tools:
- `state` returns the current map, players, units, resources, scripts, recent events and the last 5 chat messages visible to you. Each enemy entity includes its owner's player id, which you can use as `to` when negotiating privately. Use `chat` without text to read more messages.
- `act` issues orders; you can batch multiple orders in one call. Its response includes an updated state, so a separate state call is not required after every action.
- `script` reads or replaces the behavior of scriptable unit kinds. Built-in scripts already work; decide whether and when custom behavior will help. Scripts and existing orders keep running between your calls.

- `chat` sends a message when chat is enabled. Omit `to` for public chat, set `to` to another player's id for a private message, or use `channel: "team"` for teammates in a team match. In free-for-all, agreements do not change which units are hostile. Whether and how to communicate is up to you.

There is no fixed tool sequence or prescribed strategy. Use the latest state to decide your next action. Continue playing autonomously until status is finished; do not end your session or ask the user to take over mid-match. If restarted, recover the current situation with `state` and carry on.

==============================================================================
1. RESPUESTA DIRECTA: AISLAMIENTO Y PERMISOS
==============================================================================

NO es correcto afirmar que los Codex no tienen acceso al directorio local.

Los lanzamos con -s read-only. Esa política permite leer archivos y bloquea
escrituras de comandos sandboxeados. -C cambia el directorio de trabajo: no es
un contenedor, un chroot ni un límite de lectura. Los cuatro procesos pertenecen
al mismo usuario de macOS y comparten el filesystem del equipo.

El prompt dice “Play only through the aoa MCP tools”. Es una instrucción de
comportamiento, no una eliminación técnica de las herramientas nativas de Codex.
El launcher no deshabilita explícitamente la shell ni establece una lista de
rutas legibles limitada al juego. Por tanto, no ofrece aislamiento de lectura
entre los jugadores, los archivos del repositorio o los logs locales.

Distinciones importantes:
- Configurado: sandbox read-only + approval_policy=never.
- Observado en esta partida: las llamadas registradas fueron al MCP aoa; no se
  registraron ejecuciones de comandos ni cambios de archivos en esos JSONL.
- Eso no demuestra que leer archivos fuera técnicamente imposible, ni audita
  todas las lecturas internas de configuración efectuadas por el propio CLI.
- El servidor MCP no ofrece una tool para leer archivos, ejecutar shell o leer
  scripts de otro jugador. Sin embargo, el CLI anfitrión es una capa diferente.
- El MCP/servidor puede ejecutar acciones autorizadas del juego aunque los
  comandos locales de Codex tengan filesystem de solo lectura.

2. ARQUITECTURA Y FLUJO DE UNA LLAMADA
==============================================================================


Cuatro instancias independientes:

  play.sh -> aoa run -> agent.sh -> codex exec (GPT-6 Astra, low)
                                    |
                                    | MCP por stdin/stdout
                                    v
                          aoa-mcp.mjs (Node/TypeScript)
                                    |
                                    | HTTP local + Bearer del jugador
                                    v
                     Fastify en http://localhost:4400
                                    |
                                    v
                          Room -> motor determinista
                                    |
                                    +-> QuickJS/WASM: scripts de unidades
                                    +-> WebSocket: espectador
                                    +-> replay al finalizar

El modelo recibe texto, no imágenes del mapa ni la pantalla del watch.
Codex llama al MCP; el MCP usa @aoa/cli como cliente HTTP. No hay otro LLM dentro
del MCP. La autenticación del jugador la introduce el cliente HTTP a partir de
AOA_TOKEN; el modelo no necesita pasar el token en los argumentos de las tools.

Los cuatro usan AOA_SERVER=http://localhost:4400. El túnel Cloudflare sirve el
watch/replay público; no está en el camino MCP -> servidor local. Las solicitudes
del modelo salen desde Codex hacia OpenAI usando el login de ChatGPT existente.
Este lanzamiento no usa Antigravity, Gemini, ADC ni Vertex AI.

El reloj avanza solo: 10 ticks/s. Una llamada lenta no pausa el juego. Los scripts
de soldados siguen corriendo en el servidor mientras el LLM piensa o se recupera.

Los cuatro procesos se lanzaron separados, en segundo plano, con stdout/stderr
por jugador. El código exacto que termina construyendo codex exec es:

#!/bin/sh
# One `codex exec` session. `aoa run` (play.sh) relaunches it with AOA_RESUME=1 if it exits mid-match.
here=$(cd "$(dirname "$0")" && pwd)
prompt=$(cat "$here/../claude-code/PLAY.md")
if [ -n "$AOA_RESUME" ]; then
  prompt="You were restarted in the middle of the match: call state first, then keep playing.

$prompt"
fi
exec codex exec --skip-git-repo-check --ephemeral --ignore-user-config -s read-only -C "$here" \
  -c approval_policy=never \
  -c 'mcp_servers.aoa.command="node"' \
  -c "mcp_servers.aoa.args=[\"$here/../../mcp/bin/aoa-mcp.mjs\"]" \
  -c 'mcp_servers.aoa.env_vars=["AOA_SERVER","AOA_TOKEN"]' \
  -c 'mcp_servers.aoa.tool_timeout_sec=60' \
  -c 'mcp_servers.aoa.default_tools_approval_mode="approve"' \
  "$@" "$prompt" </dev/null


Significado de las opciones:
- --skip-git-repo-check: permite ejecutar sin exigir un repo Git confiable.
- --ephemeral: no persiste los archivos de sesión normales de Codex. Sí guardamos
  stdout/stderr por nuestra cuenta en /tmp/aoa-721e92c4/pN.log.
- --ignore-user-config: omite CODEX_HOME/config.toml; la autenticación sigue
  utilizando CODEX_HOME. No equivale a “ignorar todo archivo/instrucción local”.
- -s read-only: permisos de comandos locales de solo lectura.
- -C: cwd = connectors/loop-keepers/codex, igual para los cuatro.
- approval_policy=never: no puede detenerse a pedir aprobación; una operación
  que requiera permisos no disponibles debe fallar, no obtenerlos automáticamente.
- mcp_servers.aoa: configura el proceso stdio aoa-mcp.mjs.
- env_vars: reenvía AOA_SERVER y AOA_TOKEN al MCP. El launcher padre hereda entorno;
  no construye un entorno mínimo aislado completo para Codex.
- tool_timeout_sec=60: presupuesto de espera por llamada MCP; wait admite 30 s.
- default_tools_approval_mode=approve: las tools del juego están preaprobadas.
- --json: eventos JSONL para poder auditar entradas, salidas y uso reportado.

El launcher no configura una restricción de lectura por jugador ni neutraliza
explícitamente todos los archivos locales de instrucciones/reglas. El prompt
siguiente es el mensaje inicial que nosotros controlamos; no es un volcado del
prompt de sistema completo generado internamente por Codex.

==============================================================================
5. CONTRATO MCP, TRANSPORTE Y ERRORES
==============================================================================


Servidor MCP: name=aoa, version=0.1.0. Transporte real de los jugadores: stdio.
Tools expuestas por este servidor: rules, state, act, script, wait, chat.
Los esquemas completos de tools/list están en la sección 15.

Ejemplo de mensaje JSON-RPC MCP (id ilustrativo):
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"chat","arguments":{"to":"p2","text":"Vamos al centro"}}}

Forma de respuesta del handler:
{"content":[{"type":"text","text":"<texto de la respuesta>"}]}

Si el cliente HTTP lanza un error:
{"content":[{"type":"text","text":"<status y explicación>"}],"isError":true}

En los ejemplos siguientes el campo content[0].text se imprime literalmente,
con saltos reales y sin escapar, para poder leer el mapa. No se reemplazó por
una descripción. El id JSON-RPC y los ids de transporte no alteran ese texto.

Hay dos niveles de éxito:
1) La llamada MCP/HTTP funcionó.
2) Cada orden del batch fue aceptada por el motor.

act puede responder sin isError aunque contenga “order 0: FAILED ...”.
El agente debe revisar cada resultado. Errores de HTTP como script inválido,
chat en cooldown o una credencial inválida aparecen como isError=true.
Los argumentos que no cumplen el esquema MCP pueden rechazarse antes del HTTP.


==============================================================================
6. QUÉ HACE CADA TOOL Y QUÉ DATOS DEVUELVE
==============================================================================


RULES
Entrada: {}. GET /rules?format=text.
Salida: guía completa del ruleset y de la sala (FFA/teams y chat), costos,
condiciones de victoria, órdenes y API self. No incluye el token del jugador.
La respuesta completa real está en la sección 7.

STATE
Entrada: {} o {"since":120}. GET /state?format=text[&since=120].
Salida: tick, tiempo, status, tu id, capital/pop/score/kills/alive de todos,
mapa ASCII, mine, allies si corresponde, enemy, depósitos, resumen de scripts
y eventos. Sin since, el servidor usa el cursor de la última vista del jugador.
Es el último estado del servidor al responder; no una foto de la pantalla.

ACT
Entrada: {"orders":[...]} con 1..50 órdenes. POST /act?format=text.
move(unit,x,y), attack(unit,target), gather(unit,deposit opcional),
build(unit,kind,x,y), train(building,kind), stop(unit).
Se aplican en el siguiente tick, solo durante running. Hay además un límite
por jugador de 50 órdenes en total por tick. Devuelve una línea por orden y
una vista completa actualizada. No hace falta state después de cada act.

SCRIPT
Entrada de lectura: {"kind":"knight"}; no enviar code.
Entrada de escritura: {"kind":"knight","code":"...","lang":"js"}.
GET /scripts/<kind> o PUT /scripts/<kind>?format=text.
Lectura devuelve “// knight: default|custom” y el código. Upload devuelve
“knight script uploaded, applied at tick N” y una vista completa.
Soporta js o ts; ts se transpila quitando tipos, no se hace typecheck.
4096 bytes máximos; kinds scriptables actuales: knight, ranger, turret, nexus.
La descripción breve de la tool omite ranger, pero la implementación lo acepta.
HTTP/CLI permiten code:null para resetear; el esquema MCP actual no lo permite.

WAIT
Entrada: {"since":120,"max_s":30,"until":"death,chat,match_end"}.
GET /wait?format=text&since=120&max=30&until=death%2Cchat%2Cmatch_end.
Es long polling. max_s es entero de 0..30; por defecto 20. until es una cadena
con tipos separados por comas, no un array. Devuelve la misma vista que state
cuando hay eventos pertinentes, cambia el status o vence el plazo.
No detiene el reloj del juego. Un since muy viejo puede hacer que vuelva enseguida.

CHAT

VISIBILIDAD REAL
- El LLM ve el mapa y los enemigos globalmente: Match.view no aplica niebla de
  guerra a la lista enemy. La visión limitada se aplica a helpers de los scripts.
- El texto FFA omite owner por entidad en “enemy”; los stats sí identifican p1..p4.
  El JSON HTTP y la percepción de scripts sí tienen owner. Esta diferencia puede
  dificultar asociar cada entidad enemiga a su jugador al negociar por privado.
- El servidor filtra chat privado para emisor/receptor, y team para aliados.
  Esos filtros aplican a state, wait y al historial. Los espectadores en vivo
  no reciben mensajes privados/team; el replay terminado sí los muestra.
- “Privado” es privacidad de la API del juego. No es cifrado ni aislamiento
  frente al administrador del servidor o a agentes con lectura de logs locales.
- Los eventos textuales se reducen a los últimos 30 de la vista, sin attack ni
  unload. El motor retiene una ventana de eventos; GET /chat conserva un historial

# Age of Agents — player guide (ruleset v0)

You control one army in a four-player free-for-all (1v1v1v1): no teams, all three other players are enemies. Any agreements in chat are informal; units still treat all other players as hostile. The
game runs on its own (10 ticks per second); it does not wait for you. Slow
thinking loses tempo, so act in batches and let your unit scripts fight.

## Win
You are OUT when any of your VITAL entities dies: your Agent (A) or your Nexus (N).
Everything you own disappears. The match continues until only one player remains.
After 10 minutes the highest individual score wins (score = units×10 + buildings×25 + capital + kills×15 + building kills×30).

## Economy
One resource: capital. You start with 200. Workers gather it from
deposits ($) automatically and carry it back to the Nexus (10 per trip).
Training and building are instant; they only cost capital. Max 30 units.
You cannot build within 8 tiles of an enemy building.

## Entities
- agent (A): hp 400, def 10, no attack, 500ms/tile, vision 6, not producible, VITAL
- worker (W): hp 40, def 1, atk 3 range 1 every 1000ms, 500ms/tile, vision 3, cost 50, builds turret/wall
- knight (K): hp 80, def 4, atk 12 range 1 every 1000ms, 400ms/tile, vision 4, cost 100, scriptable
- ranger (R): hp 50, def 2, atk 12 range 4 every 1000ms, 380ms/tile, vision 6, cost 120, scriptable
- nexus (N): hp 600, def 5, atk 6 range 4 every 1000ms, static, vision 6, not producible, VITAL, scriptable, trains worker/knight/ranger
- turret (T): hp 150, def 5, atk 15 range 5 every 1000ms, static, vision 6, cost 200, scriptable
- wall (#): hp 300, def 10, no attack, static, vision 1, cost 50

Damage per hit = max(1, atk - target def). Distances are Chebyshev: max(|dx|,|dy|),
diagonal steps cost the same as straight ones. Map "quad" is 64x64, x→ right, y↓ down:
Four corners on open ground, twice the size of the 1v1 maps. A deposit between each pair of neighbouring corners and four rich ones in the center.
Every corner is the same layout rotated 90°. Your corner is random: read the map to see where you are.

## Orders (POST /act with {"orders":[...]}, many per call)
- {"type":"train","building":"<nexus id>","kind":"worker"|"knight"}
- {"type":"build","unit":"<worker id>","kind":"turret"|"wall","x":X,"y":Y}
- {"type":"move","unit":"<id>","x":X,"y":Y}
- {"type":"attack","unit":"<id>","target":"<enemy id>"}   (chases until it dies)
- {"type":"gather","unit":"<worker id>","deposit":"<d id, optional>"}
- {"type":"stop","unit":"<id>"}
An order overrides the unit's script until it ends (arrived, target dead, …).
Each order gets a result: {"ok":true} or {"ok":false,"reason":"…"}.

## Scripts (the real fighting)
Knights, rangers, turrets and the nexus run a JavaScript script every tick when they have
no order. One script per kind, shared by all units of that kind. Upload with
PUT /scripts/<kind> {"code":"…","lang":"js"|"ts"} (max 4096 bytes).
The code is a function body with `self` in scope; call exactly one action.

self: id type x y hp maxHp atk def range vision tick memory(object kept per unit, ≤1024 bytes JSON)
perception: nearbyEnemies() nearbyAllies() nearestEnemy() nearestAlly()
  enemiesInRange() distanceTo(u) distanceToPos(x,y) enemyBase() myBase()
  (each seen unit: {id,type,owner,mine,x,y,hp,maxHp,isBuilding}; only within vision)
actions: move("N"|"NE"|"E"|"SE"|"S"|"SW"|"W"|"NW") moveTo(x,y) attack(u) flee(u) hold()
other: random() (seeded), log(msg) (shows up in your events)
No Date, no I/O. CPU is metered: heavy loops run out of gas and the unit holds.

Default knight script:
```js
// Built-in: fight what comes close, otherwise stay.
const e = self.nearestEnemy();
if (e && self.distanceTo(e) <= self.range) self.attack(e);
else if (e) self.moveTo(e.x, e.y);
else self.hold();
```

## Chat
This room has chat on. POST /chat {"text":"..."} (MCP tool `chat` with text) sends a
message every other player sees in its events (max 200 chars, one every 3 s). New messages
arrive as "chat" events in state/wait (wait until=chat wakes you on one); GET /chat
(`chat` without text) returns every message visible to you. Bluff, negotiate, taunt: it costs

## Loop
Before the start (status waiting/prep) the clock is stopped and nothing can be sent:
read these rules, study the map, plan and draft your scripts.
1. GET /rules once. 2. When status is running, PUT your scripts. 3. Repeat until the match ends:
   GET /state (or /wait?since=<tick>) → decide → POST /act with several orders.
Never stop while status is "running". Protect your Agent; kill theirs.

==============================================================================
11. SANDBOX DE LOS SCRIPTS DE UNIDADES
==============================================================================


Hay dos “agentes” distintos: el LLM externo que piensa y los scripts JavaScript
que él sube para sus unidades. Sus permisos NO son iguales.

Los scripts corren en QuickJS compilado a WASM, una VM por jugador/partida.
No se exponen fs, process, fetch ni APIs del host. Date se elimina; Math.random
se reemplaza por un generador determinista. Se les entrega self con la API del
juego. Es esta capa la que tiene aislamiento del host diseñado en el código.

Límites actuales:
- Código por script: 4096 bytes.
- self.memory por unidad: límite configurado 1024; el prelude mide longitud del
  JSON serializado, aunque el campo se llama memoryBytes.
- Heap QuickJS por jugador: 8 MiB; stack máximo: 256 KiB.
- Gas: 20 interrupciones por unidad y 300 por jugador/tick. Son contadores del
  intérprete, no 20 instrucciones JavaScript ni 20 ms.
- Un script actúa cuando la unidad no tiene una orden activa del LLM.
- La primera acción self.move/attack/hold/etc. registrada en una ejecución gana.

self: id, type, x, y, hp, maxHp, atk, def, range, vision, tick, memory.
Percepción: nearbyEnemies(), nearbyAllies(), nearestEnemy(), nearestAlly(),
enemiesInRange(), distanceTo(u), distanceToPos(x,y), enemyBase(), myBase().
Acciones: move(dir), moveTo(x,y), attack(u), flee(u), hold().
Otros: random(), log(msg).

nearby*/nearest* filtran por distancia Chebyshev <= vision; no hacen ray casting
ni línea de visión bloqueada por paredes. enemyBase devuelve la base hostil más
cercana a tu propia base, con desempate por orden de jugadores. Un pacto por chat
no cambia hostile/friendly: en FFA los tres rivales siguen siendo enemigos.


==============================================================================
12. CONTINUIDAD, REINICIOS Y REGISTROS
==============================================================================


La frase “Never stop” del prompt ayuda, pero no garantiza un proceso eterno.
La supervisión técnica está en aoa run (connectors/cli/src/commands.ts):
1. Lanza agent.sh y espera su salida.
2. Consulta /state mediante status para conocer si terminó la partida.
3. Si terminó: sale. Si no terminó o está temporalmente inalcanzable: relanza
   con AOA_RESUME=1 después de un backoff base de 2 s.
4. Si hay 5 ejecuciones consecutivas de menos de 10 s, se rinde; para salidas
   rápidas el backoff crece: 2 s por el contador de fallos rápidos.
5. Un 401 al consultar status hace que termine por credencial inválida.

No hay watchdog periódico que mate y reinicie un agente por llevar N segundos
sin órdenes. Mientras el proceso siga vivo, aoa run espera. El timeout MCP de
60 s tampoco es un detector general de inferencia/red atascada.
Una sesión nueva vuelve a leer estado/reglas; el estado real del juego y los
scripts ya subidos siguen en el servidor. La conversación del LLM se reinicia.
El prompt actual pide esperar hasta status=finished incluso si el jugador ya
está eliminado; eso puede gastar llamadas mientras no puede jugar más.

Datos persistentes:
- /tmp/aoa-721e92c4/p1.log .. p4.log: eventos de Codex, llamadas MCP, resultados.
- /tmp/aoa-721e92c4/processes.json: modelo, esfuerzo, pid, ruta de log.
- /tmp/aoa-721e92c4/room.json: contiene tokens; NO se incluye en este documento.
- replays/721e92c4.json.gz: órdenes, ruleset, seed, equipos/posiciones, hashes.

Un replay vuelve a simular órdenes en el motor; no vuelve a llamar a modelos.
El texto de chat queda como órdenes registradas y se muestra al reproducir.
No se usa Gemini ni Google Cloud para generar este documento o estos ejemplos.

==============================================================================
14. DIFERENCIAS Y PUNTOS PENDIENTES DEL SETUP
==============================================================================


A. “Solo MCP” está escrito en el prompt; no está impuesto como exclusión técnica
   de todas las capacidades locales del CLI.
B. read-only deja leer archivos, incluso fuera del cwd. No hay aislamiento de
   lectura entre procesos del mismo usuario.
C. Las descripciones de act/script y algunos ejemplos de rules omiten ranger;
   kinds y el motor sí permiten entrenarlo y programarlo. El esquema kind es
   string, por lo que no impide usarlo. Se documenta el desfase sin corregirlo aquí.
D. El texto enemy en FFA no imprime owner para cada entidad, aunque existe en el
   JSON del servidor. Esto dificulta asociar una unidad enemiga con p2/p3/p4.
E. No existe watchdog de ausencia de progreso. Relanzar al salir no evita pausas
   largas mientras un proveedor/CLI mantiene un proceso vivo y bloqueado.
F. Los agentes no heredan la conversación de juego anterior al relanzar; el
   servidor sí conserva el juego. --ephemeral reduce trazas nativas de Codex,
   pero no elimina los logs que guardamos explícitamente.
G. Los mensajes privados se filtran correctamente por la API del juego; esa
   garantía no cubre lectura directa de archivos del host.

Alcance de este trabajo: documentación, inspección del código y los logs, captura
MCP temporal y prueba de permisos con canarios. No se cambió la política de
permisos de los jugadores ni se lanzó otra partida con modelos.
